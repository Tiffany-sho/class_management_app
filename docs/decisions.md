# 決定と未決定

**書く場所**: **覆されうる判断**とその理由 ―― 一度決めて変わったもの、まだ決まっていないもの、保留にしたもの。
確定して安定したルールは domain / data-model / architecture 側に書く。ここは「なぜ今こうなっているか」を後から追うための場所。

関連: [CLAUDE.md](../CLAUDE.md) ／ [domain.md](domain.md) ／ [data-model.md](data-model.md) ／ [architecture.md](architecture.md)

## 変わった決定

**古い記述は各ドキュメントから消し、変えた事実だけをここに残す。** どちらが正か迷わせないため。

| 決定 | 元 | 現在 | 理由 |
|------|----|------|------|
| 締め切りの設定 | 管理者が毎月手で設定する | **「毎月◯日」の繰り返しルールから自動生成** | 毎月の設定は忘れる。忘れると受付が開かず、保護者からの問い合わせで初めて気づく |
| 締め切り画面 | 生成された各月の一覧を出す | **ルールだけ。一覧は出さない** | ルールを決めれば結果は決まる。一覧を並べると「ルールと一覧のどちらが正か」が分からなくなる |
| 出席と授業記録 | 別のもの（出席をマーク／記録を書く） | **同じ1件**。`schedule_students` の1行が両方を持つ | 分けると「出欠だけある回」と「記録だけある回」ができて食い違う。保護者も2か所を突き合わせることになる |
| 欠席の回の記録 | 記録は作らない | **記録は残す**（所見が付かないだけ） | 記録が無いと「休んだのか、まだ書かれていないのか」が区別できない |
| 出席率 | 生徒一覧・生徒詳細・ホームに出す | **どこにも出さない。回数だけ出す** | 月2〜3回しか通わないので、1回休むと67%になり実態より悪く見える |
| 生徒一覧の月謝 | 月額を出す | **支払済/未払いのバッジと入金日だけ。金額は出さない** | 生徒一覧で見たいのは「誰が払っていないか」。金額を出すと月謝の一覧に見えてしまう |
| 従業員のシフト | シフトカレンダーで別途管理する | **廃止。スケジュール確定の担当コマがそのまま勤務実績** | 同じことを2回入力させることになる。`shifts` テーブルも作らない |
| 生徒の新規登録 | 生徒登録画面から行う | **ユーザー招待の中で保護者と同時に登録** | 保護者を作ってから生徒を作る2段階が、実際には必ず連続して起きる |
| 「従業員・時給設定」画面 | マスタ配下 | **「講師」に改名し、教室運用の「生徒」の直下へ** | 日々見る画面で、マスタ設定と混ざる場所ではない |
| 月謝管理・出席確認の専用画面 | それぞれ独立した画面 | **廃止。生徒一覧・生徒詳細・収入収益に統合** | 生徒を軸に見れば足りる。画面を分けるほどの量ではない |
| 講師の給与ページの月別一覧 | カードの下に一覧を置く | **カードを月送りにして一覧は廃止** | 同じ月が2か所に出ると、どちらを見ればいいか迷う |
| 「従業員」の表記 | 全画面で「従業員」 | **UI はすべて「講師」。DB のロール名は `employee` のまま** | 教室業では「講師」が自然。DB まで変えると RLS を全部書き直すことになり、得るものが表記だけなので割に合わない |
| Web アプリの画面数 | モック全画面をいきなり作る | **土台＋管理者3画面から。残りは「未実装」と出す** | DB から画面まで縦串が1本通れば、残りは同じ型をなぞるだけになる。先に横に広げると、土台の間違いが全画面に伝播する |
| アイコン | 絵文字（モックと同じ） | **線画の SVG（`components/ui/Icon.tsx`）** | 絵文字は OS ごとに形も色も変わり、shift_manage_app と揃わない。勝手に着色されるので DESIGN.md の配色の外に出る。サイズと重心も揃わない |
| 生成した型定義 | `.gitignore` に入れる | **git に含める** | 含めないとクローンしただけでは型チェックが通らず、生成には Supabase の認証情報が要る。手書き禁止・スキーマ変更後は再生成というルールは変えない |
| 収入・収益の事業別内訳 | 人件費を事業別に出す（モック） | **事業別は「コマから計算した基本給」だけ。交通費と時間外は全体に計上** | 交通費は出勤「日」に対する日額で、日曜に2教室を掛け持ちしても1日ぶん。時間外はシフト外の作業。**按分の根拠が無いものを勝手に配分すると、事業ごとの採算を誤って判断する** |
| ユーザー招待の画面 | 管理画面から招待する | **Web からは行えない。ダッシュボードから招待する** | 招待には service_role キーが要る。`VITE_` の値はバンドルに焼き込まれて配られるため、ブラウザに置くと RLS を全部素通りする鍵が公開される |
| 開催枠の編集 | マスタ画面から編集できる | **表示のみ。編集は保留** | 曜日や時間を変えると過去の勤務実績（1コマの長さ＝給与）まで変わる。どこまで遡って影響させるかを決めていない |
| 通知の作り方 | アプリから `notifications` に入れる | **DB のトリガーで作る** | アプリで作ると、ダッシュボードから直接操作したときや別の画面から同じ操作をしたときに漏れる。経路が増えるほど抜けが増える |
| 月謝の発行 | 毎月自動で作る（cron） | **管理者がボタンで発行する** | 請求は人が判断して出すもの。自動発行だと、退会の反映漏れやコース変更の途中で誤った請求が黙って出る |
| 保護者・講師の画面の分け方 | ロールごとに画面を作る | **`features/mobile/` にまとめ、ロールで中身を分ける** | 希望提出・予定・お知らせは見るものが違うだけで構造が同じ。分けると同じ修正を2か所ですることになる |
| マスタの編集 | 一覧の中で直接編集する（入力欄・切り替えボタンを行に置く） | **一覧は読むだけ。行を押してドロワーを開いてから直す** | 一覧は「探すために触る場所」。そこに入力欄があると、眺めている途中で料金が変わり、無効にするつもりのない人を無効にする。料金も在籍も**気づかないまま変わると誰も気づけない**（変更履歴が無い） |
| 希望提出 | 候補を押すたびに1件ずつ DB に書く | **選択は画面の中だけで持ち、「提出する」で1回だけ書く** | 講師は月に20コマ近く選ぶ。1タップごとに書くとその数だけ通信が走り、途中で切れたときに「どこまで出したか」が本人にも分からない。書き込みは**必ず消してから足す**（同じコマの二重登録が一意制約なので、入れ替えのときに足す側が先に走ると自分自身とぶつかる） |
| 収入・収益の2つの表 | 横に2列で並べる | **縦に並べる** | 横に割ると片方が狭くなり、金額の桁が折り返して比べられない |
| 保護者ホーム | 月謝／済んだ授業／これからの授業の3枚に分ける | **お子さま切替 → 次回の受講 → 受講状況（1枚）→ お知らせ**（モックの構成） | 済んだ回とこれからの回を別の枠に置くと、同じ月の予定を2か所で追うことになる。兄弟は教室もコースも違うので、まず1人に絞る |
| 講師の予定 | 一覧だけ | **月カレンダーが主で、一覧はその下** | 日曜は2教室が並行開催されるので、日単位で見ないと自分がどちらに入っているか分からない |
| 希望提出のボタンを押せる条件 | サーバーとの差分があるとき | **締め切り前ならいつでも押せる。選んだ数では止めない**（保護者は0件でも出せる） | 差分で判定すると、選び終えた瞬間に「変更はありません」で押せなくなる。件数で判定していた時期もあったが、希望を候補に変えた以上（下の「受講希望の件数」）止める理由が無い。内容が今のままでも押せて、そのときは「すでに提出済み」と返す（黙って何も起きない状態を作らない） |
| 給与計算の表 | 状態（確定/未確定）を出すだけ | **行から「出勤状況」のドロワーを開き、金額の根拠になったコマを1件ずつ見せる。1名だけ締めることもできる** | 金額は編集できない（コマから毎回計算しているので、直す場所はコマか時給）。数字だけ見せて直せないと、どこを直せばいいか分からない。急な欠勤で出勤が変わった人を後回しにして、確定できる人だけ先に締められるようにもした |
| 急な欠席・欠勤の反映 | スケジュール確定の画面でやる | **「当日の変更」を別画面にし、日送りにする** | あちらは「これからの月を組む」、こちらは「もう決まった日を直す」。同じ画面だと月を組んでいる途中で今日の回を触り、確定済みの勤務実績＝給与が意図せず動く |
| スケジュール確定の並べ方 | 月ぶんのコマを日ごとに全部縦に並べる | **日のカードを並べ、押した日のコマだけを下に出す** | 全部並べると縦に数十枚になり、直したい日にたどり着くまでスクロールし続ける。日のカードに**担当未定・定員超過の件数**を出し、開かずに「どの日を直すか」が決まるようにした。既定の選択も「要対応がある日」にする（先頭の日を出しても、そこが済んでいれば結局探すことになる） |
| スケジュール確定のチップ | 押すたびに足す／外すが即座に切り替わる | **下書きは押すだけで出し入れできる。確認をはさむのは確定済みのコマから外すときだけ** | 同じチップが両方に効くので、**見ているだけのつもりで触れると担当・受講が黙って消える**。ただし全部に確認を付けると、入れて外してを繰り返す組み立て作業が確認だらけになる。下書きはまだ誰にも出していないので押し直せば済むが、確定済みは保護者・講師の画面にもう出ていて、講師なら給与にも効いている。危ないのはそこだけ |
| スケジュール確定に出す人 | 割り当て済みの人は希望が無くても候補に出す（外せなくなるため） | **提出された希望だけを出す。希望の無い割り当ては人数だけ添える** | 希望を出していない人が混ざると「誰が希望を出したのか」が読めなくなる。この画面は**希望を確定に変える場所**で、それ以外の出し入れは当日の変更が受け持つ。人数と定員は実際の割り当てから来るので、黙って隠すと「2名と書いてあるのにチップが1つ」になる。数だけ添えて辻褄を合わせる |
| 幅が足りないときの文字 | 切り詰めて `…` にする（`truncate`） | **切り詰めない。** 表は縮めず横スクロール、カレンダーは狭いとき名前を出さない、氏名は幅を取り合わせない | `…` は「続きがある」ことしか伝えず、**何が省かれたか分からない**。`プログラミ…` では教室名を読み取れない。折り返しも同じで、「プログラミング教室」が3行になると幅不足なのかデータが増えたのか区別できない。**入るように作る**のが先で、それでも入らない自由記述だけ折り返しを許す |
| 表（DataTable）の幅 | `w-full` で枠に合わせる | **`w-max min-w-full`＋セルは折り返さない。枠が横スクロール** | 枠に合わせると列が潰れ、セルの中で語が折れる。表は中身の幅を保ち、足りないぶんはスクロールさせる。自由記述の列だけ `wrap: true` で折り返す（読みやすい幅で折る） |
| カレンダーのコマ表示 | セルに「教室名 + コマ数」 | **管理者は狭い画面で色 + コマ数、広い画面（900px 以上）で教室名も。講師は生徒数だけ** | 1マスは画面幅の1/7（スマホで70px）しかなく、「プログラミング」は必ず切れる。管理者が俯瞰したいのは「どの教室が何コマ動くか」だが、**講師にとってはどちらの教室かは自明**で、要るのは「何人来るか」。一度は姓も入れたが、**70px に名前と数字を並べると、その名前が相方なのか自分なのか読み取れず、数字の意味まで曇った**ので数字だけにした。誰と組むかは押して開く詳細にある。正式名称・コマ番号・講師名は `title` に残す |
| 受講希望の件数 | コースの月間回数ちょうどを選ばないと提出できない。1日1コマまで | **0件から候補ぜんぶまで。同じ日の別コマも出せる**（DB の上限トリガーと `preferences_one_per_day` を外した） | 希望は**予約ではなく候補**。回数ちょうどを選ばせると保護者が「通う日」まで決めることになり、**管理者に動かせる余地が残らない**（定員が埋まっていても差し替えられない）。多めに出してもらうほど組みやすい。実際の回数は確定（`schedule_students`）が決め、月謝は固定月額なので候補の数は請求に影響しない。同じコマの二重登録だけは一意制約で弾く |
| 見出し・行の横並び | 文字側を `min-w-0 flex-1` にしてボタンに幅を譲る | **文字側に最低幅を与える**（見出し 220px / 受信ボックスの本文 200px） | `min-w-0` は「幅0まで縮んでよい」なので、`flex-wrap` があっても**幅0で収まっている**ことになり、ボタンは次の行に落ちない。結果、375px で「スケジュール確定」が1文字ずつ8行に縦積みされ、受信ボックスの本文は 90px に潰れた。最低幅があると、入らないときにボタンのほうが下へ落ちる |
| スケジュール確定の日カード | PC で8列（`lg:grid-cols-8`） | **最大6列。1枚 160px は残す** | 8列だと PC でも1枚 120px ほどになり、「プログラミング 2」のチップが2行に折れる。日を選ぶためのカードなので、**枚数より1枚の読みやすさを優先する** |
| 通知本文の日付 | `to_char(日付, 'FMMM月FDD日')` | **`FMMM月FMDD日`** | `FM` は「先頭の0を落とす」の指示で**2文字で1つ**。`FDD` は `FM` ではなく**文字 `F` + `DD`** と読まれるので、`F` が出力に残って `8月F02日` になっていた。同じ行の `FMMM` は効いていたので、月だけ詰まって日は詰まらない中途半端な出力に。既に配った12件も直した（通知は作り直せない） |
| 狭い画面のカレンダー | 7列の升目をそのまま縮める | **640px 未満は升目をやめ、コマのある日だけを縦に並べる**（MonthDayList） | 教室が開くのは土日だけなので、月〜金の5列は1年じゅう空のまま幅の 5/7 を占める。残った2列は 375px で1マス 53px にしかならず、教室名も「コマ」の字も入らず、**数字が1つ置いてあるだけの升目**になっていた。1日1行にすれば横幅がまるごと使えて、教室名も件数も状態も言葉のまま入る。升目の値打ち（月の中の位置関係）は、そもそも入る幅があるときにしか出ない |
| 講師の予定のカレンダー | 全画面で出す | **640px 未満では出さない**（`narrow="none"`） | 狭い画面ではカレンダーも日ごとの一覧になり、下の「予定 / 終了」と同じコマが2回並ぶ。あちらは予定と終了に分かれていて情報が多いので、そちらだけ残す。**描画ごと止める**（CSS で隠すだけだと DOM に残り、読み上げにも検査にも出てくる） |
| 月謝を支払い済みにする口 | `setFeeStatus` は書いたが、**どの画面からも呼んでいなかった**（＝入金を記録する手段が無かった） | **収入・収益の「月謝の支払い状況」で行を押す → シートで記録** | 一覧の中で直接切り替えると、督促のために眺めている途中で別の生徒を支払い済みにしてしまう。月謝には変更履歴が無いので**気づかないまま変わると誰も気づけない**（マスタ編集と同じ理由）。入金日は今日を既定にするが直せる ―― 通帳を見ながら後からまとめて記録するとき、勝手に今日にされると突き合わせられない。金額とメモも同じシートで直せる（ドメインルール10。それまで実装されていなかった） |
| 見た目の検査 | jsdom で「切り詰めの指定が残っていないか」まで見る | **本物の Chrome を開いて実寸を測る**（`npm run check:layout`） | jsdom はレイアウトを計算しないので、**折り返しは原理的に測れない**。実際、文字を大きくしたときに出席リストの氏名が3行に折れていたのを、jsdom のテストは1本も落とさずに通した（文字は全部見えているので「切り詰めていない」は成立する）。端末の Chrome を使うので Chromium のダウンロードは要らない |
| 画面の文字サイズ | `text-[12px]` のような固定 px を直に書く | **`ui-2xs`〜`ui-3xl` の9段を `clamp()` で持ち、画面幅に追従させる**（app-tokens.js） | 固定 px はスマホに合わせると PC で小さく、PC に合わせるとスマホで溢れる。ブレークポイントで段階的に変えると境界で見た目が飛び、指定も `sm: md: lg:` で3倍になる。rem で書くのは**利用者がブラウザの標準文字サイズを大きくしているときに一緒に大きくするため**。DESIGN.md はアプリシェルの文字サイズを規定していないので、design-tokens.js には足さず別ファイルに置く（あちらは shift_manage_app と揃える必要がある） |
| 保護者・講師の画面の教室名 | どの画面にも教室名を書く | **本人が関わる教室が1つなら書かない。2つにまたがる人にだけ出す**（`multiBusiness`） | 保護者はきょうだいごと同じ教室、講師は担当1教室が普通なので、書いても読む前から分かっていることを繰り返すだけで、日付・時間・生徒・出欠を押しのける。ただし DB は掛け持ちを許している（`employee_businesses` は多対多）ので、**「今は誰もまたがっていないから」で消し込まない**。またがる人が現れた日に、どちらのコマか読めない画面になる |
| 保護者の画面のコマ番号 | 「第〇コマ」を日付に添える | **保護者には出さない。時刻だけ**（講師・管理者には残す） | 第〇コマは教室の内部の並び順で、保護者が知りたいのは「何時からか」。時刻を見れば何コマ目かは分かるが、逆は分からない |
| 保護者ホームの月謝 | 受講状況の見出し行に小さなバッジで添える | **独立したカードにする。ただし金額は出さず「未払い / 支払い済み / 請求前」だけ**。未払いは面ごと赤系 | 保護者がこのアプリで確かめたいのは「払ったかどうか」。**金額は固定月額なので毎月同じで、変わらない数字をいちばん大きく出すと、変わる情報（支払い状況）がその横に埋もれる**。金額は請求書と教室が持っている。**モックには無い構成**（モックは受講状況の中に置いていた）。月を切り替えたあとに戻ってきたとき分からなくなるので、カードに月を必ず書く |
| 保護者ホームの回数の集計 | 「済んだ授業 n / これから n」を出す | **出さない** | すぐ下に1件ずつ並んでいるものを数え直しただけで、数えて分かることが増えない。出席率も出さない（月2〜3回なので1回休むと 67% になり実態より悪く見える） |
| 講師の勤務一覧 | 日付・コマ番号・時刻・教室名・生徒数・「AとBで2名体制」を1件ずつ | **「いつ・何時から・何人」だけ。押すとその1コマの詳細が開く。「予定」と「終了」に分ける** | 残りは押して開く先に置けば足りる。混ぜて日付順に並べると、開いた瞬間に目に入るのが月初＝もう終わった回になり、いちばん確かめたい「次はいつか」を毎回スクロールして探すことになる。見出しは「これから／終わった」ではなく**予定／終了**（口語より、予定表の語のほうが短くて迷わない） |
| 講師の「担当」画面 | 月ぶんの担当コマを一覧で並べ、行に授業記録の入力欄を置く | **モックどおり 直近の担当 → 出席 → 同日の自分の担当 の3段。記録は押して開く** | 開いて確かめたいのは「次はいつで、誰が来るか」。月の一覧に埋もれると毎回探す。入力欄が並ぶと出欠のボタンも押しにくい。ただし**未記録の過去コマだけは別枠で残す** ―― モックのままだと、休んだ日の記録を後から入れる手段がどこにも無くなる |
| 講師が見るコマの絞り込み | RLS が返さないので画面では絞らない | **画面側で「自分が担当するコマ」に絞る** | 前提が誤りだった。`schedules` の select は「管理者 または 確定済み」なので、**確定したコマは担当外の教室のぶんも全員に見える**（行に個人情報が無いのでその設計自体は正しい）。絞らないと他の講師のコマが自分の予定として並ぶ。実際に SQL で確かめたら、講師に見える今月30コマのうち自分のぶんは8コマだった |
| 生徒名・講師名 | 一覧画面でだけ行を押して開く | **どこに出ていても名前を押せば詳細が開く**（id ひとつで引く共有シート） | 名前を見て素性を確かめたくなる場面は画面を問わず起きる。行データを揃えて渡す形にすると、名前しか持っていない画面からは開けない |
| 講師に見せる生徒・講師の情報 | 管理者と同じものを出す | **生徒は月謝と保護者名を出さない。講師は労働条件と連絡先を出さない** | 月謝と保護者名は RLS が講師に**そもそも返さない**ので、出そうとしても空欄になる。講師の労働条件はルール12。連絡先を伏せるのは、教室の連絡を管理者経由にする運用だから。**画面の分岐は権限の実装ではない**（権限は RLS 側にある） |
| 当日の変更で講師を足す口 | 「代わりに入れる:」（外した人の代役として置く） | **「講師を追加」。足せる人がいないときは「講師」ページで担当教室を設定する、と行き先まで出す** | 代役としてしか入れられないと読めると、**単に1名増やしたいときに押す場所が無いように見える**。プログラミング教室は講師が2名しかいなくて全員が毎コマ入っているので、「全員入っています」で行き止まりになる状態が普通に起きる。足せる相手をその教室の担当講師に限るのは、時給が教室ごとに決まるうえ DB も複合外部キーで縛っているため |
| 月謝を調整したときの保護者への伝え方 | 管理者のメモが出るだけ（調整そのものは伝わらない） | **調整のあった月だけ「金額を見直しました（増額／減額）」を出す** | 保護者の月謝カードは金額を出さない方針なので、**調整に気づく手段がどこにも無かった**。請求書が届いてから問い合わせになる。金額を出す方針に戻さず、動いた月にだけ出す（毎月出すと意味が消える）。増減の向きまで書くのは、「見直しました」だけでは慌てて確かめるべきか分からないため |
| 「調整された月」の判定 | （判定手段が無かった） | **`fees.base_amount`（発行時の額）との差で判定する** | `amount` は発行時にコースの月額をコピーして管理者が上書きするので、値だけからは上書きの有無が分からない。`courses.monthly_fee` と突き合わせるのは誤りで、**料金を改定した瞬間に過去の全月が「調整された」ことになる**。既存行は調整の有無が分からないので調整なしとして埋めた（証明できないことを画面に書かない） |
| 確定した月の希望提出画面 | 候補日を全部並べたまま（提出済みにチェックが付き、全部押せない） | **決まった日のカードだけを出す。締め切りの帯も提出ボタンも出さない** | 確定後にいちばん知りたいのは「結局どの日に決まったのか」なのに、それがどこにも書かれていなかった。候補6件のうち2件が決まった月でも、画面には6件にチェックが付いて見える。押せないものを並べると「まだ変えられるのでは」と探させる |
| 受講希望の DB テスト（A20 / B04〜B07） | 「1日1コマ」「コースの回数まで」を弾くことを確かめていた | **上限が無いこと（回数超過・同じ日の別コマ・0件）を確かめる** | ルール2の変更でその制限自体が無くなったのに、テストだけが古い規則を主張して落ち続けていた。**制限がこっそり戻っていないか**を見る側に書き換えた |
| draft のコマを前提にした DB テスト（F03 / F04b / F19b / G01） | 本番に未確定のコマが残っていることを当てにしていた | **テストの中で draft のコマを作る（rollback で消える）** | 全部確定した瞬間に「0件」を見るだけの検査になった。**F03 は0件を期待しているので、ポリシーが外れていても通ってしまう。** 見たい状態は自分で用意する |
