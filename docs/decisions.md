## 変わった決定

**古い記述は各ドキュメントから消し、変えた事実だけをここに残す。** どちらが正か迷わせないため。

| 決定 | 元 | 現在 | 理由 |
|------|----|------|------|
| 締め切りの設定 | 管理者が毎月手で設定する | **「毎月◯日」の繰り返しルールから自動生成** | 毎月の設定は忘れる。忘れると受付が開かず、保護者からの問い合わせで初めて気づく |
| 締め切り画面 | 生成された各月の一覧を出す | **ルールだけ。一覧は出さない** | ルールを決めれば結果は決まる。一覧を並べると「ルールと一覧のどちらが正か」が分からなくなる |
| 出席と授業記録 | 別のもの（出席をマーク／記録を書く） | **同じ1件**。`schedule_students` の1行が両方を持つ | 分けると「出欠だけある回」と「記録だけある回」ができて食い違う。保護者も2か所を突き合わせることになる |
| 欠席の回の記録 | 記録は作らない | **記録は残す**（所見が付かないだけ） | 記録が無いと「休んだのか、まだ書かれていないのか」が区別できない |
| 出席率 | 生徒一覧・生徒詳細・ホームに出す | **どこにも出さない。回数だけ出す** | 月2〜3回しか通わないので、1回休むと67%になり実態より悪く見える |
| 生徒一覧の月謝 | 月額を出す | **支払済/未払いのバッジと入金日だけ。金額は出さない** | 生徒一覧で見たいのは「誰が払っていないか」。金額を出すと月謝の一覧に見えてしまう |
| 従業員のシフト | シフトカレンダーで別途管理する | **廃止。スケジュール確定の担当コマがそのまま勤務実績** | 同じことを2回入力させることになる。`shifts` テーブルも作らない |
| 生徒の新規登録 | 生徒登録画面から行う | **ユーザー招待の中で保護者と同時に登録** | 保護者を作ってから生徒を作る2段階が、実際には必ず連続して起きる |
| 「従業員・時給設定」画面 | マスタ配下 | **「講師」に改名し、教室運用の「生徒」の直下へ** | 日々見る画面で、マスタ設定と混ざる場所ではない |
| 月謝管理・出席確認の専用画面 | それぞれ独立した画面 | **廃止。生徒一覧・生徒詳細・収入収益に統合** | 生徒を軸に見れば足りる。画面を分けるほどの量ではない |
| 講師の給与ページの月別一覧 | カードの下に一覧を置く | **カードを月送りにして一覧は廃止** | 同じ月が2か所に出ると、どちらを見ればいいか迷う |
| 「従業員」の表記 | 全画面で「従業員」 | **UI はすべて「講師」。DB のロール名は `employee` のまま** | 教室業では「講師」が自然。DB まで変えると RLS を全部書き直すことになり、得るものが表記だけなので割に合わない |
| Web アプリの画面数 | モック全画面をいきなり作る | **土台＋管理者3画面から。残りは「未実装」と出す** | DB から画面まで縦串が1本通れば、残りは同じ型をなぞるだけになる。先に横に広げると、土台の間違いが全画面に伝播する |
| アイコン | 絵文字（モックと同じ） | **線画の SVG（`components/ui/Icon.tsx`）** | 絵文字は OS ごとに形も色も変わり、shift_manage_app と揃わない。勝手に着色されるので DESIGN.md の配色の外に出る。サイズと重心も揃わない |
| 生成した型定義 | `.gitignore` に入れる | **git に含める** | 含めないとクローンしただけでは型チェックが通らず、生成には Supabase の認証情報が要る。手書き禁止・スキーマ変更後は再生成というルールは変えない |
| 収入・収益の事業別内訳 | 人件費を事業別に出す（モック） | **事業別は「コマから計算した基本給」だけ。交通費と時間外は全体に計上** | 交通費は出勤「日」に対する日額で、日曜に2教室を掛け持ちしても1日ぶん。時間外はシフト外の作業。**按分の根拠が無いものを勝手に配分すると、事業ごとの採算を誤って判断する** |
| ユーザー招待の画面 | 管理画面から招待する | **Web からは行えない。ダッシュボードから招待する** | 招待には service_role キーが要る。`VITE_` の値はバンドルに焼き込まれて配られるため、ブラウザに置くと RLS を全部素通りする鍵が公開される |
| 開催枠の編集 | マスタ画面から編集できる | **表示のみ。編集は保留** | 曜日や時間を変えると過去の勤務実績（1コマの長さ＝給与）まで変わる。どこまで遡って影響させるかを決めていない |
| 通知の作り方 | アプリから `notifications` に入れる | **DB のトリガーで作る** | アプリで作ると、ダッシュボードから直接操作したときや別の画面から同じ操作をしたときに漏れる。経路が増えるほど抜けが増える |
| 月謝の発行 | 毎月自動で作る（cron） | **管理者がボタンで発行する** | 請求は人が判断して出すもの。自動発行だと、退会の反映漏れやコース変更の途中で誤った請求が黙って出る |
| 保護者・講師の画面の分け方 | ロールごとに画面を作る | **`features/mobile/` にまとめ、ロールで中身を分ける** | 希望提出・予定・お知らせは見るものが違うだけで構造が同じ。分けると同じ修正を2か所ですることになる |
| マスタの編集 | 一覧の中で直接編集する（入力欄・切り替えボタンを行に置く） | **一覧は読むだけ。行を押してドロワーを開いてから直す** | 一覧は「探すために触る場所」。そこに入力欄があると、眺めている途中で料金が変わり、無効にするつもりのない人を無効にする。料金も在籍も**気づかないまま変わると誰も気づけない**（変更履歴が無い） |
| 希望提出 | 候補を押すたびに1件ずつ DB に書く | **選択は画面の中だけで持ち、「提出する」で1回だけ書く** | 講師は月に20コマ近く選ぶ。1タップごとに書くとその数だけ通信が走り、途中で切れたときに「どこまで出したか」が本人にも分からない。書き込みは**必ず消してから足す**（上限チェックが行ごとのトリガー、1日1コマが一意制約なので、上限のまま日を差し替えると足す側が先に走った時点で弾かれる） |
| 収入・収益の2つの表 | 横に2列で並べる | **縦に並べる** | 横に割ると片方が狭くなり、金額の桁が折り返して比べられない |
| 保護者ホーム | 月謝／済んだ授業／これからの授業の3枚に分ける | **お子さま切替 → 次回の受講 → 受講状況（1枚）→ お知らせ**（モックの構成） | 済んだ回とこれからの回を別の枠に置くと、同じ月の予定を2か所で追うことになる。兄弟は教室もコースも違うので、まず1人に絞る |
| 講師の予定 | 一覧だけ | **月カレンダーが主で、一覧はその下** | 日曜は2教室が並行開催されるので、日単位で見ないと自分がどちらに入っているか分からない |
| 希望提出のボタンを押せる条件 | サーバーとの差分があるとき | **選択がコースの回数ぶん揃っているとき**（講師は1コマ以上） | 差分で判定すると、**上限まで選び終えた＝出せる状態になった瞬間に「変更はありません」で押せなくなる**。揃っていないときは押せない代わりに残り数を出す。内容が今のままでも押せて、そのときは「すでに提出済み」と返す（黙って何も起きない状態を作らない） |
| 給与計算の表 | 状態（確定/未確定）を出すだけ | **行から「出勤状況」のドロワーを開き、金額の根拠になったコマを1件ずつ見せる。1名だけ締めることもできる** | 金額は編集できない（コマから毎回計算しているので、直す場所はコマか時給）。数字だけ見せて直せないと、どこを直せばいいか分からない。急な欠勤で出勤が変わった人を後回しにして、確定できる人だけ先に締められるようにもした |
| 急な欠席・欠勤の反映 | スケジュール確定の画面でやる | **「当日の変更」を別画面にし、日送りにする** | あちらは「これからの月を組む」、こちらは「もう決まった日を直す」。同じ画面だと月を組んでいる途中で今日の回を触り、確定済みの勤務実績＝給与が意図せず動く |
| スケジュール確定の並べ方 | 月ぶんのコマを日ごとに全部縦に並べる | **日のカードを並べ、押した日のコマだけを下に出す** | 全部並べると縦に数十枚になり、直したい日にたどり着くまでスクロールし続ける。日のカードに**担当未定・定員超過の件数**を出し、開かずに「どの日を直すか」が決まるようにした。既定の選択も「要対応がある日」にする（先頭の日を出しても、そこが済んでいれば結局探すことになる） |
| スケジュール確定のチップ | 押すたびに足す／外すが即座に切り替わる | **下書きは押すだけで出し入れできる。確認をはさむのは確定済みのコマから外すときだけ** | 同じチップが両方に効くので、**見ているだけのつもりで触れると担当・受講が黙って消える**。ただし全部に確認を付けると、入れて外してを繰り返す組み立て作業が確認だらけになる。下書きはまだ誰にも出していないので押し直せば済むが、確定済みは保護者・講師の画面にもう出ていて、講師なら給与にも効いている。危ないのはそこだけ |
| スケジュール確定に出す人 | 割り当て済みの人は希望が無くても候補に出す（外せなくなるため） | **提出された希望だけを出す。希望の無い割り当ては人数だけ添える** | 希望を出していない人が混ざると「誰が希望を出したのか」が読めなくなる。この画面は**希望を確定に変える場所**で、それ以外の出し入れは当日の変更が受け持つ。人数と定員は実際の割り当てから来るので、黙って隠すと「2名と書いてあるのにチップが1つ」になる。数だけ添えて辻褄を合わせる |
| 幅が足りないときの文字 | 切り詰めて `…` にする（`truncate`） | **切り詰めない。** 表は縮めず横スクロール、カレンダーは狭いとき名前を出さない、氏名は幅を取り合わせない | `…` は「続きがある」ことしか伝えず、**何が省かれたか分からない**。`プログラミ…` では教室名を読み取れない。折り返しも同じで、「プログラミング教室」が3行になると幅不足なのかデータが増えたのか区別できない。**入るように作る**のが先で、それでも入らない自由記述だけ折り返しを許す |
| 表（DataTable）の幅 | `w-full` で枠に合わせる | **`w-max min-w-full`＋セルは折り返さない。枠が横スクロール** | 枠に合わせると列が潰れ、セルの中で語が折れる。表は中身の幅を保ち、足りないぶんはスクロールさせる。自由記述の列だけ `wrap: true` で折り返す（読みやすい幅で折る） |
| カレンダーのコマ表示 | セルに「教室名 + コマ数」 | **狭い画面は色 + コマ数だけ。広い画面（900px 以上）で教室名も出す** | 1マスは画面幅の1/7しかなく、「プログラミング」は必ず切れる。教室名は真下の凡例が担う。正式名称は `title` に持たせて、押さなくても確かめられるようにした |
| 講師の「担当」画面 | 月ぶんの担当コマを一覧で並べ、行に授業記録の入力欄を置く | **モックどおり 直近の担当 → 出席 → 同日の自分の担当 の3段。記録は押して開く** | 開いて確かめたいのは「次はいつで、誰が来るか」。月の一覧に埋もれると毎回探す。入力欄が並ぶと出欠のボタンも押しにくい。ただし**未記録の過去コマだけは別枠で残す** ―― モックのままだと、休んだ日の記録を後から入れる手段がどこにも無くなる |
| 講師が見るコマの絞り込み | RLS が返さないので画面では絞らない | **画面側で「自分が担当するコマ」に絞る** | 前提が誤りだった。`schedules` の select は「管理者 または 確定済み」なので、**確定したコマは担当外の教室のぶんも全員に見える**（行に個人情報が無いのでその設計自体は正しい）。絞らないと他の講師のコマが自分の予定として並ぶ。実際に SQL で確かめたら、講師に見える今月30コマのうち自分のぶんは8コマだった |
| 生徒名・講師名 | 一覧画面でだけ行を押して開く | **どこに出ていても名前を押せば詳細が開く**（id ひとつで引く共有シート） | 名前を見て素性を確かめたくなる場面は画面を問わず起きる。行データを揃えて渡す形にすると、名前しか持っていない画面からは開けない |
| 講師に見せる生徒・講師の情報 | 管理者と同じものを出す | **生徒は月謝と保護者名を出さない。講師は労働条件と連絡先を出さない** | 月謝と保護者名は RLS が講師に**そもそも返さない**ので、出そうとしても空欄になる。講師の労働条件はルール12。連絡先を伏せるのは、教室の連絡を管理者経由にする運用だから。**画面の分岐は権限の実装ではない**（権限は RLS 側にある） |
| 当日の変更で講師を足す口 | 「代わりに入れる:」（外した人の代役として置く） | **「講師を追加」。足せる人がいないときは「講師」ページで担当教室を設定する、と行き先まで出す** | 代役としてしか入れられないと読めると、**単に1名増やしたいときに押す場所が無いように見える**。プログラミング教室は講師が2名しかいなくて全員が毎コマ入っているので、「全員入っています」で行き止まりになる状態が普通に起きる。足せる相手をその教室の担当講師に限るのは、時給が教室ごとに決まるうえ DB も複合外部キーで縛っているため |

## 保留中の判断

### 中学卒業後の扱い
学年が中3（=9）を超えた生徒を在籍終了にするか、継続用のコースを用意するか。**判断は保留。**
それまでは進級処理の一覧に出して管理者に知らせるだけとし、**システムからは自動で何もしない**。

## 未決定事項（実装前に要確認）

### 業務ルール

- **定員オーバー・希望が通らなかった場合** — 管理者が調整するだけか、保護者に通知するか
- **年度をまたぐデータの扱い** — 過去年度の保持期間、退会した生徒の扱い
- **授業記録を書いたとき保護者に通知するか** — 現状は通知を出さず、マイページに出るだけ。通知すると毎回届くので多すぎるかもしれない
- **固定費（家賃・光熱費・教材費）を収支に入れるか** — 現状は人件費だけ。入れるならマスタが要る

### 技術

- **shift_manage_app とのアカウント統合** — 従業員は両アプリを使う。ログインが2つになるが v1 では別で良いか
- **iOS リポジトリの作成タイミング** — Web が動いてから作るか、先に骨組みだけ用意するか
